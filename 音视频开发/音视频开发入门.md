## 2.3 音视频协议概述

在音视频开发领域，编解码、封装、字幕、传输格式等大体可以按照如下进行分类：
- 原始音视频格式：
	- 原始音频格式有：[[音视频开发/音视频开发入门#^yygq77|PCM]]
	- 原始图像格式有：RGB、YUV等
	此时为未压缩的原始音视频格式
- 编解码协议/格式：
	- [[音视频开发/音视频开发入门#^rqasow|音频编码格式]]有：AAC、MP3、Opus、...
	- [[音视频开发/音视频开发入门#^q5iiwu|视频编码格式]]有：H.264/AVC、H.265/HEVC、AV1、VP9、...
	此时的数据是一串压缩后的二进制流(或者说是ES，Elementary Stream)，此时仍无法传输
- [[音视频开发/音视频开发入门#^csrxcg|封装协议/格式]]，即把一路或多路二进制流(ES)封装打包在一起，并携带时间戳、轨道信息等
	- MPEG2-TS
	- FLV
	- MP4
	- MOV、MKV、AVI等
	此时这些数据可以用于写入文件，也可以作为网络负载进行发送
- [[音视频开发/音视频开发入门#^wuxkce|音视频传输协议]]，即把上述封装好的若干数据包进行网络传输的协议
	- RTP
	- TS over UDP/TCP
	- RTMP
	- HTTP-FLV
- 控制&指令协议，控制流的播放、暂停、统计、丢包反馈等
	- RTSP
	- RTCP
上述协议的排列顺序也即为音视频从底到顶的编码、封装、传输以及控制协议。

## 2.5 视频编码格式概述 ^q5iiwu

### 2.5.1 H.264简介与入门

#### 2.5.1.1 基础帧类型(I、P、B、SP、SI帧)

严格来讲，H.264中的每个图片由一个或多个切片(slice)组成，而slice又分为如下五种类型：
- <font color="#9bbb59">I帧</font>：<font color="#9bbb59">帧内图像编码帧</font>(Intra-coded Picture)：
	- <font color="#c00000">I帧是关键帧</font>
	- <font color="#c00000">只使用本帧内部的信息来进行压缩，不参考其他帧</font>
	- 采用类似JPEG压缩的DCT压缩技术，可达1/6压缩比且无明显压缩痕迹
- <font color="#9bbb59">P帧</font>：<font color="#9bbb59">前向预测编码图像帧</font>(Predictive-coded Picture)，
	- <font color="#c00000">P帧参考之前的帧</font>(I帧或P帧)<font color="#c00000">进行编解码</font>，<span style="background:#fff88f"><font color="#c00000">可能参考前面多个离散帧</font></span>
	- 当某个参考帧丢失时，<font color="#c00000">会导致随后一连串依赖该帧的P/B帧解码异常</font>
	- 其做运动补偿预测，并只编码差异值
- <font color="#9bbb59">B帧</font>：<font color="#9bbb59">双向预测编码图像帧</font>(Bi-Predicted Picture)
	- <font color="#c00000">B帧既参考之前</font>，<font color="#c00000">又参考之后的帧进行编解码</font>
	- <font color="#c00000">B帧压缩率最高</font>，但解码更耗费资源
- <font color="#9bbb59">SP帧</font>：(Switching P)
	- 专为不同码流之间无缝切换设计的P帧
	- 现代主流编码器一般不再生成SP/SI帧
- <font color="#9bbb59">SI帧</font>：(Switching I)
	- 用于配合SP帧实现码流切换的I帧
	- 现代主流编码器一般不再生成SP/SI帧
<font color="#c00000">因此其中常用的只有I帧、P帧、B帧这三种</font>。此外，由于B帧既参考之前的帧，又参考之后的帧，因此会存在<font color="#9bbb59">解码器重排</font>现象。

#### 2.5.1.2 其他基本概念

- <font color="#9bbb59">IDR帧</font>：<font color="#9bbb59">即时编码刷新</font>(Instantaneous Decoding Refresh)：
	- 实际上IDR并不是一种独立的帧类型，而是特殊的I帧
	- <font color="#c00000">其在I帧的基础上额外添加了"立即刷新"的约束</font>，即立即刷新关键帧(由于P帧可能会参考前面多个帧，甚至参考I帧之前的帧。<font color="#c00000">而IDR可以切断参考链</font>)
- <font color="#9bbb59">SPS</font>：序列参数集，
- <font color="#9bbb59">PPS</font>：图像参数集
- <font color="#9bbb59">GOP</font>：<font color="#9bbb59">图像序列</font>(Group Of Picture)：
	- 两个I帧之间的图像序列+一个I帧
- <font color="#9bbb59">解码器重排</font>：由于B帧同时参考两个方向的帧，因此解码B帧时必须先解码其所依赖的后续的帧。此现象就叫作解码器重排现象。
- <font color="#9bbb59">DTS</font>：<font color="#9bbb59">解码时间戳</font>，帧数据送入解码器解码的时间。其出现主要是由于解码器重排。
- <font color="#9bbb59">PTS</font>：<font color="#9bbb59">显示时间戳</font>，解码后的帧被显示的时间。其出现主要是由于解码器重排。
- <font color="#9bbb59">RBSP</font>：<font color="#9bbb59">原始字节序列载荷</font>，原始字节载荷
- <font color="#9bbb59">EBSP</font>：<font color="#9bbb59">封装字节序列载荷</font>，可以理解为为了避免与包格式冲突而"转义"后的字节载荷

#### 2.5.1.3 基本数据格式

H.264编码主要由一系列的NALU(NAL Unit)组成，其基本结构为：

| Start code | NALU header |      NALU payload       |
| :--------: | :---------: | :---------------------: |
|   3或4字节    |   1 Byte    | 若干字节<br>(封装字节序列载荷，EBSP) |

或没有 `Start Code` 的形式 ：

| NALU header |      NALU payload       |
| :---------: | :---------------------: |
|   1 Byte    | 若干字节<br>(封装字节序列载荷，EBSP) |

注：
- <font color="#c00000">当H.264使用字节流形式存储时</font>，<font color="#c00000">其需要添加</font> `Start code` ，<font color="#c00000">用于对</font> `NALU` <font color="#c00000">进行分割</font>
- <font color="#c00000">而当其已经被更高级的容器封装时</font>，<font color="#c00000">就不再需要</font> `Start code` 
即：

```text
# 当使用字节流形式时(如硬盘中存储、网络传输等)，H.264数据流为：
[Start Code][NALU Header][NALU Payload][Start Code][NALU Header][NALU Payload]...[Start Code][NALU Header][NALU Payload]

# 当使用更高级分片容器存储时，H.264数据流为：
- [NALU Header][NALU Payload]
- [NALU Header][NALU Payload]
- ...
- [NALU Header][NALU Payload]
```


其具体每个部分定义如子章节所示。

##### 2.5.1.3.1 Start Code

起始码字段有如下两种形式，功能与含义一样：
- `0x00 00 01` 
- `0x00 00 00 01` 
正如上文所述，<font color="#c00000">Start Code用于对</font> `NALU` <font color="#c00000">进行分割</font>。<font color="#c00000">而在Payload中也有对应的机制避免出现与</font> `Start Code` <font color="#c00000">相同的编码</font>。

##### 2.5.1.3.2 NAL头

```text
+----------------+----------------+-----------------------------+
| forbidden_zero |  nal_ref_idc   |        nal_unit_type        |
|      1 bit     |     2 bits     |            5 bits           |
+----------------+----------------+-----------------------------+
       bit7         bit6 ~ bit5             bit4 ~ bit0
```

其中：
- `forbidden_zero` ：错误标志位
	- 正常时为0
	- 为1时表示流中出现了语法错误或比特错误
- `nal_ref_idc` ：表示该NALU对解码参考的重要性
	- 其值越大则越重要，越不应被丢弃
- `nal_unit_type` ：标明这个NALU是什么类型，包含IDR、SPS、PPS等，具体如下：
	![[Resources/chrome_x5aqNiaNYe.png]]

##### 2.5.1.3.3 NALU Payload

正如上文所述，NALU的分割完全依赖于Start Code，因此在Payload中需要避免出现 `0x000001` 或 `0x00000001` 。其具体规定为：
1. 当连续两个 `0x00` 出现
2. 且其后跟随 `0x00` / `0x01` / `0x02` / `0x03` 时
<font color="#c00000">会在上述两个</font> `0x00` <font color="#c00000">后插入一个</font> `0x03` ，从而将<font color="#9bbb59">RBSP</font>转化为<font color="#9bbb59">EBSP</font>。

## 2.6 音频格式及编码基础 ^rqasow

音频格式中的重要参数：
- 采样率：每秒对原始模拟音频数据的采样次数
- 量化位数：将采样数据舍入到整数时，保留的整数位长度

### 2.6.1 PCM ^yygq77

<font color="#9bbb59">PCM</font>全名为<font color="#9bbb59">Pulse Code Modulation</font>，即<font color="#9bbb59">脉冲编码调制</font>。是一种<font color="#c00000">原始的音频数据</font>，其将模拟信号经采样、量化、编码转换而变成了标准的数字音频数据，主要流程如下图所示。
	![[Resources/chrome_zBxsD51jDG.png]]
在上图流程中：
- <font color="#9bbb59">采样</font>：按照一定的<font color="#9bbb59">采样率</font>进行采样，例如采样率为44.1kHz，则代表每秒采样44.1k次
- <font color="#9bbb59">量化</font>：将采样到的数据舍入到一个整数表示的过程，整数的长度叫<font color="#9bbb59">位深</font>
- <font color="#9bbb59">编码</font>：将量化后的信号转换为二进制数据
在PCM中，还有如下的几个参数来描述PCM数据：
- 符号位：表示样本诗句是否有符号位，例如1Byte的数据在有符号位时表示 $-128 \sim 127$ ，无符号时表示 $0 \sim 255$ 。
- 字节序：规定大小端
- 整型或浮点型：表示数据使用的是整型还是浮点型，大多数情况下使用整型，要求高的场合使用浮点型

### 2.6.2 AAC

<font color="#9bbb59">AAC</font>全名为<font color="#9bbb59">Advanced Audio Coding</font>，即<font color="#9bbb59">高级音频编码</font>。是一种音频数据的文件压缩格式，具体而言，AAC可分为ADIF和ADTS两种文件格式，具体如下：
- <font color="#9bbb59">ADIF</font>：Audio Data Interchange Format，即<font color="#9bbb59">音频数据交换格式</font>。<font color="#c00000">其解码要求必须从明确定义的开始处进行解码，而不能从数据流的中间开始解码</font>。因此其通常用于存放到文件系统中。
- <font color="#9bbb59">ADTS</font>：Audio Data Trasport Stream，即<font color="#9bbb59">音频数据传输流</font>。<font color="#c00000">其数据流中有同步字比特流，解码可以从数据流中的任意位置开始</font>。

其中，ADTS的数据结构为 `header+body` 形式，即：

```text
┌────────────────┌───────────────────────────┐
│     Header     │     Body                  │
└────────────────└───────────────────────────┘
```

其 `Header` 由固定头(28bit)和可变头(28bit)组成。
其固定头格式为：

| <center>key</center>       | size   | <center>含义</center>              |
| -------------------------- | ------ | -------------------------------- |
| `syncword`                 | 12 bit | 固定为 `0xFFF`                      |
| `ID`                       | 1 bit  | MPEG标志，`0=MPEG-4` ，`1=MPEG-2`    |
| `layer`                    | 2 bit  | 固定为 `00`                         |
| `protection_absent`        | 1 bit  | CRC缺席标志，`0=enable` ，`1=disable`  |
| `profile`                  | 2 bit  | AAC Profile                      |
| `sampling_frequency_index` | 4 bit  | 采样率索引                            |
| `private_bit`              | 1 bit  | 私有位                              |
| `channel_configuration`    | 3 bit  | 声道配置，`1=单声道` ，`2=双声道` ，`5=5.1` 等 |
| `original_copy`            | 1 bit  | 原版/拷贝标志                          |
| `home`                     | 1 bit  | 一般为0                             |

其可变头格式为：

| <center>key</center>                 | size   | <center>含义</center>                    |
| ------------------------------------ | ------ | -------------------------------------- |
| `copyright_identification_bit`       | 1 bit  |                                        |
| `copyright_identification_start`     | 1 bit  |                                        |
| `aac_frame_length`                   | 13 bit | AAC帧长度(头+数据+CRC)，单位字节                  |
| `adts_buffer_fullness`               | 11 bit | 缓冲区占满程度，常见流里一般为 `0x7FF`                |
| `number_of_raw_data_blocks_in_frame` | 2 bit  | 当前帧中 `raw_data_block` 的个数<br>通常为0，表示1个 |

## 2.7 字幕格式及编码基础

常见字幕格式包含 `SRT` 、 `SSA` 、 `ASS` 等格式。

### 2.7.1 SSA

SSA即SubStation Alpha，比传统的SRT格式

SSA是类ini风格的纯文本文件，其主要包含如下五个section(但并非必须全部出现)：
- `[Script Info]` ：包含头部和总体信息，且必须为第一行
- `[v4 Styles]` ：包含了所有样式的定义，每一个
- `[Events]` ：包含了所有脚本的事件
- `[Fonts]` ：包含内嵌字体的信息
- `[Graphics]` ：包含内嵌图片的信息

### 2.7.2 ASS

ASS即Advanced SubStation Alpha，其基于SSA 4.0进行改进和构建，其增加了更多的特效及指令。

其在SSA字段中有如下改进：
- `[v4 Styles]` ：改名为 `[v4+ Styles]` 

## 2.8 音视频封装协议 ^csrxcg

### 2.8.1 FLV

FLV即Flash Video，由Adobe公司设计，其适用于视频流传输以及直播等场景。其组成也主要由 `Header` 和 `Body` 组成：

```text
┌────────┌───────────────────┌───────┌───────────────────┌─────
│ Header │ PreviousTagSize#0 │ Tag#1 │ PreviousTagSize#1 │ ...
└────────└───────────────────└───────└───────────────────└─────
```

#### 2.8.1.1 Header

FLV Header通常由9个字节(或更多)组成，具体如下：

| <center>Key</center> | size   | <center>含义</center>                                                                |
| -------------------- | ------ | ---------------------------------------------------------------------------------- |
| `Signature`          | 8 Bit  | 始终为字符 `'F'`                                                                        |
| `Signature`          | 8 Bit  | 始终为字符 `'L'`                                                                        |
| `Signature`          | 8 Bit  | 始终为字符 `'V'`                                                                        |
| `Version`            | 8 Bit  | 数值类型版本号，例如 `0x01` 代表版本 `1`                                                         |
| `TypeFlagsReserved`  | 5 Bit  | 保留字段，必须为0                                                                          |
| `TypeFlagsAudio`     | 1 Bit  | 为 `1` 时表示有音频                                                                       |
| `TypeFlagsReserved`  | 1 Bit  | 保留字段，必须为0                                                                          |
| `TypeFlagsVideo`     | 1 Bit  | 为 `1` 时表示有视频                                                                       |
| `DataOffset`         | 32 Bit | 数据偏移量，版本为 `1` 时最小为9(<font color="#c00000">即Header大小</font>)<br>大于9时表示header中还有拓展信息 |

#### 2.8.1.2 Body

FLV Body由一个个的Tag组成，每个Tag下有4字节空间记录该Tag的长度。
以下方的结构示意为例：

```text
┌────────┌───────────────────┌────────┌───────────────────┌────
│ Header │ PreviousTagSize#0 │ Tag#1  │ PreviousTagSize#1 │ ...
│        │ (uint32_t, 4bit)  │ (data) │ (uint32_t, 4bit)  │    
└────────└───────────────────└────────└───────────────────└────
```

其Body中：
- `PreviousTagSize` 正如其名，指定前一个Tag的尺寸。例如：
	- `PreviousTagSize#n` 代表第 `n` 个Tag的尺寸
	- <font color="#c00000">而对于第一个</font> `PreviousTagSize`，即 `PreviousTagSize#0` <font color="#c00000">来说</font>，<font color="#c00000">其尺寸值为</font> `Header` 的size。
- `Tag` <font color="#c00000">即数据荷载</font>，可能包含视频、音频、脚本这三种类型数据。
	- 每个 `Tag` 只会包含一类数据
	- `Tag` 的具体定义可见子章节

#### 2.8.1.3 PreviousTagSize

`PreviousTagSize` 即 `uint32_t` 类型的尺寸信息。

#### 2.8.1.4 Tag

FLV的Tag本质是数据荷载，其数据结构定义如下：

| field               | size   | <center>含义</center>                                                      |
| ------------------- | ------ | ------------------------------------------------------------------------ |
| `TagType`           | 8 bit  | 数据荷载类型，仅包含如下三种：<br>- `8=audio`<br>- `9=video`<br>- `18=script`<br>其他类型保留 |
| `DataSize`          | 24 bit | `Data` 区数据长度                                                             |
| `Timestamp`         | 24 bit | 相对于第一个tag的毫秒时间戳。首个tag的时间戳一定为0                                            |
| `TimestampExtended` | 8 bit  | 兼容 `signed int32_t` 的高8位时间戳拓展                                            |
| `StreamID`          | 24 bit | 始终为0                                                                     |
| `Data`              |        | 数据荷载，尺寸等同 `DataSize` 中数值。<br>内容定义见章节[[音视频开发/音视频开发入门#^t5f8of\|Tag Data]]。 |

#### 2.8.1.5 Tag Data ^t5f8of

##### 2.8.1.5.1 音频数据包

对于音频数据，其又有如下数据结构：

| field           | size  | <center>含义</center>                                                                                           |
| --------------- | ----- | ------------------------------------------------------------------------------------------------------------- |
| `SoundFormat`   | 4 bit | 音频数据类型，其支持PCM、MP3、AAC等类型数据。<br>具体定义见规范                                                                        |
| `SoundRate`     | 2 bit | 采样率枚举，其支持：<br>- `0=5.5khz`<br>- `1=11khz`<br>- `2=22khz`<br>- `3=44khz`                                       |
| `SoundSize`     | 1 bit | 表示采样深度，`0` 表示8位采样，`1` 表示16为采样                                                                                 |
| `SoundType`     | 1 bit | 表示单声道(`0`)或立体声(`1`)                                                                                           |
| `AACPacketType` | 8 bit | 当且仅当 `SoundFormat=10` 时存在(即AAC)，表示AAC包类型：<br>- `AACPacketType=0` 时表示为AAC序列头<br>- `AACPacketType=1` 时表示为AAC裸数据 |
| `SoundData`     |       | 音频数据                                                                                                          |

##### 2.8.1.5.2 视频数据包

对于视频数据，其有如下数据结构：

| field       | size  | <center>含义</center>                                                                       |
| ----------- | ----- | ----------------------------------------------------------------------------------------- |
| `FrameType` | 4 bit | 帧类型，包含                                                                                    |
| `CodecID`   | 4 bit | <font color="#c00000">编码器ID</font>，包含：<br>- JPEG(现已不使用)<br>- H.263<br>- Screen video<br>等 |
| `VideoData` |       | 视频数据，其内部格式根据 `CodecID` 而定                                                                 |
其 `FrameType` + `CodecID` 共计1字节，可以视作是Video Tag Data的header。

##### 2.8.1.5.3 脚本数据包

脚本数据包通常只有一个，且会放置到flv的第一个Tag中(即跟在FLV Header之后)。用于存放视频的元信息，例如：
- `duration` ：持续时长
- `frame rate` ：视频帧率
- `creator` ：创作者
- `width` ：视频宽度
- `height` ：视频高度
等。其通常包含两个AMF包，即[[音视频开发/MISC/AMF#^w701pn|AMF0]]和[[音视频开发/MISC/AMF#^m9lr93|AMF3]]。

### 2.8.2 MPEG2-TS

在学习TS协议之前，应当先了解[[音视频开发/MPEG协议族/MPEG协议族概述#^t843fd|MPEG协议族概述]]：
![[音视频开发/MPEG协议族/MPEG协议族概述#2 MPEG协议族概述 t843fd]]

而TS是MPEG-2协议族下属的一种<font color="#c00000">流式封装格式</font>，因此TS协议的全名应当为MPEG2-TS。而从其名 `TS` 角度来讲，<font color="#9bbb59">TS</font>即<font color="#9bbb59">Transport Stream</font>，传输流。其规范定义于ISO/IEC 13818-1
TS包通常可以分为如下两类：
	![[Resources/MPEG2-TS组成.drawio.svg]]
其中：
- PES即存放音视频数据的数据包，其数据种类包含视频流、音频流、字幕、私有数据等
- PSI Section主要存放音视频流的说明信息、解码信息等，其数据主要包含：
	- PAT表
	- PMT表
	- CAT表
	等

而对于PES类数据包，其结构可以分为如下三层：
	![[Resources/MPEG2-TS_PES层结构.drawio.svg]]
其中：
- ES层：压缩编码后的音视频数据
- PES层：在ES层的基础上加入了时间戳(PTS/DTS)等信息
- TS层：在PES层的基础上加入了数据流识别信息和传输信息，固定为188字节
注：
- TS中<font color="#c00000">可能存放PES</font>，<font color="#c00000">也可能存放PSI表</font>(PAT、PMT、CAT、SDT、EIT等)

#### 2.8.2.1 TS层

如上述章节所述，TS层是MPEG2-TS协议的传输包单元，其固定为188字节。其分为如下三个部分：
- `TS Header` ：头部信息，固定4个字节
- `Adaptation Field` ：调整字段，可能存在也可能不存在
- `Payload` ：数据荷载，存放PES、PAT或PMT等数据

##### 2.8.2.1.1 TS Header

`TS Header` 的数据结构如下图所示(了解即可)：
	![[Resources/chrome_bPox977zh4.png]]
其中：
- 上图中第一行为TS数据包格式，第二行开始为 `TS Header` 格式
- `Adaption field` 被算入到了 `header` 中
- 其字段有：
	- `sync byte` ：同步字节，固定为 `0x47`
	- `transport error indicator` ：传输错误指示符
	- `payload unit start indicator` ：负载单元起始标示符，当其为 `1` 时标示一个完整数据包的开始
	- `transport priority` ：传输优先级，`1` 标示高优先级
	- `PID` ：`Packet ID` ，表示当前<font color="#c00000">数据包分组</font>，<font color="#c00000">其对应荷载</font><span style="background:#fff88f"><font color="#c00000">即对应分组的流数据</font></span>。随后其对应流数据按对应组规则进行解析。
		- 常见值有：
			- `0x0000` ：PAT表
			- `0x0001` ：CAT表
			- `0x0002` ：TSDT表
			- `0x0012` ：EIT,ST
			- `0x0013` ：RST,ST
	- `transport scrambing control` ：传输加扰控制，`00` 标示未加密
	- `adaptation field control` ：是否包含 `Adaption field` ：
		- `00` 为保留
		- `01` 为无 `Adaption field` ，仅包含 `Payload`
		- `10` 为仅包含 `Adaption field` ，无 `Payload`
		- `11` 为同时包含上述两者
	- `continuity counter` ：递增计数器，从 `0x00` 到 `0x0f` ，起始值不一定为0，但是一定递增

##### 2.8.2.1.2 Adaptation field

继续关注于下图(了解即可)：
	![[Resources/chrome_bPox977zh4.png]]
其中：
- 第二行为 `TS Header` 的数据结构示意图，第三行即为 `Adaptation field` 的数据结构示意图
- 其字段有：
	- `adaptation field length` ：表示从下一字节开始计算的 `Adaptation field` 的长度
	- `discontinuty indicator` ：表示当前TS包不连续状态，`1` 为真
	- `random access indicator` ：
	- `elementary stream priority indicator` ：
	- `PCR flag` ：表示调整字段中是否包含 `PCR` (节目时钟参考)
	- `OPCR flag` ：表示调整字段中是否包含 `OPCR` 
	- `Splicing point flag` ：表示调整字段中存在拼接点
	- `Transport private data flag` ：表示调整字段中至少存在一个私有数据
	- `Adaptation field extension flag` ：表调整字段是否存在拓展
补充：
- 在MPEG2-TS规范中，<font color="#c00000">并没有规定哪些类型的数据包不能携带调整字段</font>，也就是所有类型的数据包均可携带调整字段。但是通常：
	- 如下类型的数据包通常不携带调整字段：
		- PAT表
		- PMT表
	- 而在视频流和音频流中通常都需要添加调整字段，通常添加在一个帧的第一个和最后一个ts包中

#### 2.8.2.2 PES层

<font color="#9bbb59">PES</font>的全名为<font color="#9bbb59">Packetized Elementary Stream</font>，是打包的原始比特流(ES)。
而正如上述章节所述，PES是在ES层的基础上加入了时间戳(PTS/DTS)等信息，其用于传输音视频、字幕等数据。
继续回到原先的TS-PES-ES结构图：
	![[Resources/MPEG2-TS_PES层结构.drawio.svg]]
由于ES层数据包都比较大，因此PES会对ES包进行分割，并在<font color="#c00000">第一个ES前</font>加上 `PES Header` 。

##### 2.8.2.2.1 PES Header

`PES Header` 的结构定义如下图所示：

其中：
- `packet start code prefix` ：固定的24bit起始前缀，固定值为 `0x000001`
- `stream id` ：用于指示PES包的数据类型，其中：

	- `0xe0` ：表示视频
- `PES pactet length` ：表示该字段后的PES包长度。其可以指定为0，表示其未指定或限定长度
